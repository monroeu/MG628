01

Structured, unstructured, or semi-structured?

Managers should not treat all data as one thing. A relational table has a fixed schema. Human language has no fixed row-and-column structure. JSON sits between those extremes: it has recognizable keys and tags, but records can contain different fields.

Structured

Organized into a predefined schema such as rows, columns, data types, and relationships.

Examples: SQL tables, billing records

Unstructured

Human-readable content without a fixed machine-oriented schema.

Examples: customer reviews, clinical notes

Semi-Structured

Uses keys, tags, or metadata, but does not require every record to have the same fields.

Examples: JSON, XML

4. I don't trust it yet. I'm worried about my data security and privacy.

6. The bill payment feature is excellent, but the app freezes whenever I try to check my transaction history.
7. I sent money to the wrong number and customer support helped me reverse it quickly. Great service!
8. App interface is confusing. I accidentally paid twice for the same bill because the button didn't respond.
9. Security features like PIN and fingerprint make me feel safe, but I wish there was two-factor authentication.
10. Merchant payments work perfectly, but money transfers to other users fail about 30% of the time.

06

Connect the evidence

WHY TWO DATA TYPES?

Logs can tell TPay that a transaction failed. They cannot fully explain frustration, confusion, trust, or why customers might leave. The reviews add context the logs do not carry.

The assignment asks you to interpret transaction patterns, not only one row. Consistent short cycle times suggest reliability; long or highly variable cycle times raise operational risk.
