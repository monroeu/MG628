## Deployment method (browser GitHub)
1. Visit https://github.com/monroeu/MG628 and select the **main** branch.
2. Use **Add file → Upload files** and drop the `visualization-labs` directory's folder structure; GitHub web upload behavior varies, so verify nested paths in the preview. Alternatively use GitHub Desktop to copy the folder into the local repository and commit/push.
3. Confirm GitHub Pages is already enabled under **Settings → Pages** and publishing from the correct branch/root; this repository already hosts its course website.
4. After Pages publishes, open:
   - `https://monroeu.github.io/MG628/visualization-labs/`
   - `https://monroeu.github.io/MG628/visualization-labs/powerbi/`
   - `https://monroeu.github.io/MG628/visualization-labs/tableau/`
5. Add this optional link to the existing course homepage **without replacing the homepage**:

```html
<a href="./visualization-labs/">Power BI &amp; Tableau Interactive Laboratories</a>
```

## Important limits
- These pages are hosted as static GitHub Pages resources, but optional authenticated Supabase progress and evidence submission is now integrated.
- Checkboxes are cached locally and sync to Supabase after the student signs in and the instructor publishes the lab offering. Exported notes remain a downloadable backup.
- `.pbix` and `.twbx` files cannot be generated by a browser-only HTML manual; students create them in their BI tools.
- The uploaded assignment PDF repeats healthcare visuals in a public administration deliverables section; the lab separates the pathways and gives a proposed 100-point rubric rather than misrepresenting the PDF's inconsistent line numbering.
- The supplied housing DimDate contains only 2024; the lab teaches a calendar repair or use of project start dates. Healthcare dates cover the fact table's 2024 admission/discharge range.
- This release copies the eleven supplied datasets into clean predictable paths and does not modify the original data.
- Do not publicly publish identifiable patient/contact data via Tableau Public; use locally and/or de-identify before sharing.

## Dedicated Power BI measure table (required)
Before entering the healthcare or housing DAX formulas, students must complete the **Create an empty Measures table first** module in `powerbi/index.html`: Home → Enter data → leave grid empty → name `_Measures` → Load; then create each measure by right-clicking `_Measures` → New measure, hide placeholder Column1, and optionally set display folders. Leave the table disconnected. Calculated columns remain in their dimension/fact tables.


## Supabase integration (October 2026)

The laboratory package includes `supabase/visualization_labs.sql`, `supabase/functions/visualization-lab-api/index.ts`, `assets/supabase-config.js`, `assets/cloud-lab.js`, and `instructor/index.html`. The new Edge Function is standalone; it does not replace `student-auth-api`, `student-portal-api`, `participation-api`, or `instructor-api`.

The SQL creates progress and submission tables with RLS enabled and no direct browser grants, a private `mg628-lab-submissions` bucket, and Power BI/Tableau assignments with **unpublished** offerings for existing active MG628 sections. In your Instructor Control Center, publish the relevant offering and set opens/due/closes dates when ready.

For new students: authenticate through `/MG628/student/` first. The visualization labs reuse the existing Supabase Auth browser session when available; they do not create a second account. If your existing student portal stores tokens in a nonstandard client storage key, the session must be bridged in that portal (or a student can sign in via a standard Supabase Auth client).

Instructor review page: `/MG628/visualization-labs/instructor/` (separate review panel; requires instructor role in Supabase). The main Instructor Control Center can link to this panel; no existing `instructor/index.html` file has been overwritten.

**Security:** all queries are mediated by an authenticated Edge Function; enrollment and the course/assignment pairing are verified on every student action; instructor access is verified server-side; files are kept in private storage. No service-role credential appears in the static HTML.

### Important login compatibility test
The cloud client uses the default Supabase Auth browser session. If the current `/student/` application stores the session under a custom key, students may see a login prompt despite having signed in. In that case align both pages' Supabase Auth `storageKey` or provide a safe authenticated cross-page session bridge in the existing portal. Never paste access tokens into URLs or store service role keys in HTML. This has not yet been live-tested with a student account.
